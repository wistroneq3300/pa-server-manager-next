1 PA Manager — 專案是什麼

Wistron PA Server Manager：AI GPU 伺服器(與機櫃)的集中式網頁管理台，把 L10(單機) 與 L11(機櫃) 監控/控制統一在一個畫面。被控主機不用裝 agent，全靠 SSH(OS) + IPMI/BMC 溝通。歷史 telemetry 存 SQLite；瀏覽器內的終端機由獨立的 node/ssh2 bridge 提供。

  • 後端 FastAPI (Python 3.12)；前端 原生 JavaScript(無 framework、無 build step)
  • GitHub: https://github.com/wistroneq3300/pa-server-manager
  • 本機 checkout: /root/sheng/manager/pa_manager(git remote 指到上面 repo)

功能重點

L10 單機

系統增刪 / OS SSH、BMC、硬體清單(CPU/DIMM/SSD/GPU/NIC)、sensor 即時與歷史、sensor AI 診斷、電源控制、GPU 資訊。

L11 機櫃

機櫃平面圖(U 槽)、拓樸圖、整櫃 telemetry、機櫃 AI 分析。

Terminal / 廣播

瀏覽器內 xterm(OS+BMC)、系統廣播(一次送指令到多台)。

KVM

單機 KVM(noVNC→BMC RFB)、KVM 同步廣播、SP-X 自動登入 broker。

AI Copilot

自然語言操作界面，接本機 vLLM(見下方「AI 如何接 vLLM」)。

測試資料庫

測試項目庫(testlib)管理、上傳 / 管理與檢視。

1 從零 Build（乾淨機器 / 乾淨 clone）

前置需求：Linux + Python 3.12 + Node.js 18+。

Step 1 — 抓程式碼

git clone https://github.com/wistroneq3300/pa-server-manager.git
cd pa-server-manager

Step 2 — Python 環境 + 依賴

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Step 3 — Terminal bridge 的 node 依賴

cd terminal_bridge
npm ci          # 用 package-lock.json（ssh2 + ws）
cd ..

Step 4 — 準備資料目錄

程式讀 PA_DATA_DIR 環境變數（沒設就用程式所在目錄）。生產建議獨立資料夾：

export PA_DATA_DIR=/srv/pa-manager-prod/data
mkdir -p "$PA_DATA_DIR"

首次啟動資料夾是空的也行，上線後在網頁「Add System」建機台。若遷移既有站，就把舊的 data.json 與 telemetry.db 複製進去。

Step 5 — 啟動（試跑 vs 正式）

試跑（port 8788）：

source .venv/bin/activate
PORT=8788 bash run.sh
# http://localhost:8788/

正式（systemd, port 6969）：

sudo cp pa-manager.service pa-terminal-bridge.service /etc/systemd/system/
# ⚠️ 一定要編輯兩支 unit：WorkingDirectory、ExecStart 的 python 路徑、
#    Environment PA_DATA_DIR，都改成這台機器的實際路徑
sudo systemctl daemon-reload
sudo systemctl enable --now pa-terminal-bridge   # 先起 node bridge
sudo systemctl enable --now pa-manager           # 再起 python 後端
sudo systemctl status pa-manager pa-terminal-bridge
兩支服務都要跑，且 pa-terminal-bridge 要能讀同一個 $PA_DATA_DIR/data.json(它從這裡取機台帳密，不信任前端傳的密碼)。

Step 6 — 驗證

  • 開 http://<host>:6969/ UI 有出來
  • System Manager 加一台(OS IP/user/pass) → 開 web terminal 確認 SSH 通
  • 開某機台/機櫃 Telemetry → AI 分析那幾行有繁體中文摘要(代表 vLLM 通)

2 安裝方式（重裝 / 新機器復刻）

Step 2 — systemd unit

[Unit]

[Service]

也有現成的管理 script：/opt/openhands/agent-canvas-ctl.sh start|stop|restart|status(PID-file based)。

OpenHands 不是直接改 settings 指向模型，而是用 LLM profile 管理；每個 profile 是一個 JSON，指到一個 OpenAI-compatible endpoint。目前 4 個 profile 對應 4 顆 vLLM：

deepseek-v4-flash (預設)openai/deepseek-v4-flashhttp://127.0.0.1:18011/v1vllm-flash
qwen3.8-27bopenai/qwen3.8-27bhttp://127.0.0.1:18003/v1vllm-27b
qwen3-vl-32bopenai/qwen3-vl-32bhttp://127.0.0.1:18004/v1vllm-vl
qwen3-coderopenai/qwen3-coderhttp://127.0.0.1:18002/v1vllm-coder

profile 檔範例結構（api_key 欄位是加密後的值，複製既有 profile 改 model+base_url 最快）：

{
  "model": "openai/deepseek-v4-flash",
  "api_key": "<encrypted>",
  "auth_type": "api_key",
  "base_url": "http://127.0.0.1:18011/v1",
  "num_retries": 5, "timeout": 300,

開一個新 conversation 想用別顆模型 → 在 UI 用 switch_llm 選 profile 即可。預設 agent 用哪顆 → 看 /root/.openhands/agent-profiles/default.json 的 llm_profile_ref。

3 vLLM — 總覽與硬體

3 三大魔鬼細節（踩過坑，最常再犯）

① B200 NCCL/NVLS 卡死（TP≥2 必看，flash 就是這樣解）

B200 的 NVLink SHARP / NVLS multicast 與 torch symmetric memory 路徑在 TP≥2 時會 hang（all_reduce 永不回傳、port 不 listen）。一定要：

export NCCL_SOCKET_IFNAME='=lo'      # 單機 loopback，避開 USB NIC
export NCCL_IB_DISABLE=1            # 單機不走 IB
export NCCL_NVLS_ENABLE=0           # ★ 關 NVLink SHARP/NVLS multicast（hang 主因）
export VLLM_ALLREDUCE_USE_SYMM_MEM=0 # 關 torch symmetric memory
# 啟動參數再加：--disable-custom-all-reduce（讓 vLLM 只走 PYNCCL）

成功時 NCCL log 會看到 0 nvls channels + via P2P/CUMEM；vLLM log 看到 Using ['PYNCCL'] all-reduce backends。不要 NCCL_P2P_DISABLE=1(要保留 NVLink P2P)；不要手動 export RANK/WORLD_SIZE。

② flash 的 TP 不能 =3

DeepSeek V4 有 64 attention heads，64/3 不整除 → validation error。TP 必須是 1/2/4/8。目前用 TP4 (GPU0-3)。

③ 這台只有 7 張卡 (0~6)

不要設 CUDA_VISIBLE_DEVICES=7 或超過的 index —— 會 NVML InvalidArgument crash-loop。另：--served-model-name "a b"(空白) 在 vLLM 0.28 會被當單一字串 id，不是多 alias，命名要用單一 token。
